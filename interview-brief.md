# Интервью-бриф: «Финансовый календарь»

> Документ — результат интервью с заказчиком (он же основной пользователь). Предназначен агенту, который будет составлять ТЗ.
> Дата интервью: 16.11.2026. Все решения ниже приняты заказчиком явно; места, где заказчик пошёл против рекомендации интервьюера, помечены **⚠ Риск**. Открытые вопросы — в разделе 14.

---

## 1. Суть продукта

Настольное macOS-приложение — **календарь денежного потока вперёд** с ручным вводом. Не трекер расходов «куда ушли деньги», а инструмент, который отвечает на два вопроса:

1. **«Хватит ли мне денег до даты X?»** — прогноз остатка и кассовых разрывов (главное).
2. **«Когда я достигну цели Y?»** — накопления и закрытие долгов.

Плюс моделирование сценариев «что если» поверх этих двух ответов.

Анализ прошлого (структура расходов) — второстепенен.

## 2. Проблема и исходный кейс

- Сейчас заказчик ведёт финансы в **Google-таблице**.
- **Реальный кейс:** не учёл дополнительные списания и фактические повседневные траты → к концу месяца **не хватило 8 000 ₽**. Причина — не забытый крупный платёж, а отклонение повседневных трат от плана, замеченное слишком поздно.
- **Боли Google-таблицы** (все названы заказчиком):
  - нет календарного вида;
  - повторяющиеся платежи приходится копировать вручную;
  - нет прогноза остатка;
  - нельзя быстро проиграть сценарий;
  - нет графиков;
  - нет уведомлений о событиях.

**Ключевой инсайт для ТЗ:** продукт должен ловить кейс «8 000 ₽» **в середине месяца**, а не в конце — через свободный остаток с резервами (§6.3) и фактический темп трат (§6.5).

## 3. Пользователи

- Основной пользователь — заказчик.
- В одном приложении **несколько профилей = разные люди** (например, члены семьи на одном Маке). Данные профилей изолированы логически.
- dmg может раздаваться близким; репозиторий на GitHub **публичный**, приложение может скачать любой.
- Мультипользовательской синхронизации/общего бюджета нет.

## 4. Реальная финансовая картина заказчика (пример данных для ТЗ)

| Элемент | Значение |
|---|---|
| Доход | Только зарплата, ~**180 000 ₽/мес**, фиксированная сумма и дата |
| Структура счетов | Одна **карта-хаб** (зарплатная): с неё оплачиваются кредиты, кредитка, аренда, покупки, переводы на накопительные счета; иногда деньги возвращаются с накопительных обратно |
| Аренда | 30 400 ₽/мес, «к дате платежа деньги должны быть» |
| Кредиты/рассрочки | 4 шт. (регулярные платежи с датой окончания) |
| Кредитная карта | 1 шт., покупки по ней **не делаются**; вносится обязательный платёж + иногда «сверху», чтобы закрыть |

**Цели заказчика:**

| Цель | Сумма | Срок | ≈ в месяц |
|---|---|---|---|
| Закрыть кредитку | 300 000 | 3 года | 8 300 |
| Досрочно закрыть кредит/рассрочку | 100 000 | 1 год | 8 300 |
| Отпуск | 180 000 | 6 мес | 30 000 |
| Машина | 3 000 000 | 5 лет | 50 000 |
| Подушка безопасности | не названа | — | — |
| Дом | не названа | — | — |

**Наблюдение интервьюера:** 180 000 − 30 400 (аренда) − ~97 000 (цели) ≈ 52 600 на три оставшихся кредита и всю жизнь. План целей, вероятно, неисполним — именно поэтому приложение должно честно показывать «план не сходится». Этот набор данных — хороший тестовый пример для ТЗ.

## 5. Платформа и технологии

- **Только macOS, только десктоп.** Мобильной версии нет. ⚠ Риск, принятый осознанно: сверка остатка возможна только за компьютером → реже, чем хотелось бы.
- **Стек:** Tauri (Rust) + React + TypeScript + SQLite с миграциями + системные уведомления macOS (UNUserNotificationCenter) + GitHub Actions (тесты и сборка `.dmg`).
- **Новый проект с нуля** (не форк и не модуль другого приложения).
- **Без** глобальных хоткеев и компактного вида.
- **Данные только локально** (SQLite). Облака и синхронизации нет.
- **Автобэкап** — автоматически, в отдельную папку на том же компьютере. Отказ диска/системы — принятый риск.
- **Экспорт** (CSV/JSON) — не нужен.
- Публичный репозиторий → в ТЗ обязательно: `.gitignore` и проверка в CI, что файлы БД/бэкапов/личные данные не коммитятся.
- **Touch ID при открытии приложения** — один раз на всё приложение.
- **Язык** — только русский. Форматы: `1 250 000 ₽`, `16.11.2026`, неделя с понедельника.
- **Тема:** светлая и тёмная, выбор пользователя.

## 6. Функциональные решения

### 6.1. Счета

- Несколько счетов: основная карта-хаб, накопительные, **счёт-долг**.
- **Переводы** между счетами — отдельный тип события, не считаются ни доходом, ни расходом.
- Счета делятся на «доступные» (для прогноза «хватит ли») и «отложенные/долговые».
- **Счёт-долг** (кредитка, кредит с целью досрочного закрытия): хранит текущую сумму долга, **обновляемую вручную** (например, по выписке). Обязательный платёж — регулярный перевод с хаба на счёт-долг (с флагом «обязательный»), «сверху» — разовый перевод (уточнено решением В14, §16). Показывается ориентировочная дата закрытия при текущем темпе. **Проценты не считаются**, точность ±месяц допустима.
- Кредиты/рассрочки по умолчанию — регулярный платёж с **обязательной датой окончания** (после неё платёж исчезает из прогноза). Если есть цель досрочного закрытия — кредит ведётся как счёт-долг с остатком.
- **Начальный остаток:** по умолчанию 0. Событие «−5 000» в пустом приложении даёт остаток −5 000. Реальная опорная точка задаётся **сверкой на дату** — остаток пересчитывается от неё в обе стороны (в прошлое и будущее). Можно вводить события задним числом. История за прошлые месяцы специально не импортируется.
- **Удаление счёта:** система предлагает выбор — (1) оставить события без счёта, (2) удалить вместе со счётом, (3) перенести на другой счёт.
- **События без счёта** — справочные: видны в календаре серым с пометкой, **на остатки и прогноз не влияют**, могут быть привязаны к счёту позже.

### 6.2. События и движок повторений (**главная функция по мнению заказчика**)

- Типы: поступление, списание, перевод между счетами, корректирующее «Неучтённое» (системное, из сверки).
- **Повторения:** выразительность уровня iCalendar RRULE (RFC 5545) — частота, интервал, дни недели, числа месяца, позиции («последний», «второй вторник»), исключения + **произвольный список дат**.
- **UI повторений:** основные сценарии — отдельными кнопками-пресетами («каждый день», «будни», «выходные», «еженедельно», «ежемесячно», «ежеквартально», «ежегодно», «выбрать даты»), под ними — расширенный конструктор. При создании — подсказка со списком ближайших дат.
- **Окончание:** бессрочно / до даты / N раз. Для рассрочек дата окончания обязательна.
- **Граничные случаи:** «31-е» в коротком месяце → последний день месяца.
- **Перенос с нерабочих дней:** автоправило у события (назад / вперёд / не переносить) с подсказкой при создании. Учитывается **производственный календарь РФ** (праздники и переносы). Предложение интервьюера, не оспоренное заказчиком: календарь встроен в приложение на известные годы и обновляется с релизом; для отсутствующих лет — фоллбэк «только сб/вс» с пометкой в UI; ручное добавление нерабочего дня. Онлайн-обновления нет (данные только локальные).
- **Ручной сдвиг** конкретного вхождения (например, зарплата пришла раньше).
- **Редактирование регулярных** — три режима, как в Google Календаре: только это вхождение / это и все следующие / все. История изменений сохраняется (аренда до марта 30 400, после — 33 000).
- **Индексация** у любого регулярного события — на выбор: **плавно** (ежемесячно, сложный процент, например «+10% за год» для продуктов) или **ступенькой** (раз в год с даты). Каждое вхождение после индексации округляется до целого рубля, погрешность не переносится.
- **Горизонт прогноза: 20 лет.** Требование к производительности: пересчёт прогноза на весь горизонт при изменении события ≤ ~1 с.
- **Удаление:** сразу, без корзины, но **всегда с диалогом подтверждения**, описывающим масштаб («Удалить регулярное событие „Аренда“ и 238 будущих вхождений?»).
- **Суммы:** только рубли, целые рубли.

### 6.3. Повседневные траты, резервы и свободный остаток

- **Гибридный учёт:** повседневка не вводится по каждой покупке; закладывается **по шаблону дней недели** (например, будни 800 ₽/день, выходные 2 500 ₽/день; возможны отдельные правила на конкретный день недели). Отдельные траты можно вносить по желанию; крупные и нерегулярные вносятся всегда.
- **Резерв под обязательный платёж** (аренда, кредиты, кредитка): часть денег карты помечается как уже занятая.
- **Свободный остаток** = остаток основной карты − резервы под ещё не списанные обязательные платежи.
- **Отображение в календаре** — остаток **основной карты** + суммы поступлений и списаний дня.
- **Сигналы (красный/жёлтый) и предупреждения** считаются по **свободному остатку**.
- При наведении — разбивка: «на карте 42 000 · зарезервировано 30 400 · свободно 11 600».
- Остальные счета — на отдельной вкладке «Счета» со своими графиками; в календаре видны только переводы на них и с них как события основной карты.

### 6.4. План → факт

- **Подтверждение событий — гибрид:** флаг у события «подтверждать автоматически» / «требует подтверждения». По умолчанию: списания — требуют подтверждения, зарплата — авто.
- Наступившее неподтверждённое событие висит в статусе «ожидает подтверждения», продолжает учитываться в прогнозе и подсвечивается. Действия: «✓ прошло» (можно поправить сумму/дату) / «✗ не было».
- **Сверка остатка:** пользователь вводит фактический остаток → разница с расчётным оформляется **корректирующим событием типа «Неучтённое»** на дату сверки (видно в истории и в аналитике план/факт).

### 6.5. Фактический темп трат

- Прогноз повседневки остаётся по шаблону, но показывается фактический темп: «тратите 1 050/день против плана 800 → к концу месяца −7 500».

### 6.6. Кассовый разрыв

- Предупреждение о кассовом разрыве с **датой и суммой**.
- В первой версии — **только предупреждение**, без автоматических предложений по исправлению.
- В тексте предупреждения учитывается приоритет целей («отчисление на отпуск 10-го создаёт разрыв»).

### 6.7. Цели

- **Виртуальные цели:** несколько целей могут жить на одном счёте (на накопительном 200 000: 120 000 «подушка» + 80 000 «отпуск»).
- **У цели есть план отчислений** → приложение считает дату достижения и проверяет, не создают ли отчисления разрыв.
- **Параметры «2 из 3»:** сумма, срок, взнос — любые два, третье считается.
- **Копилка без цели:** только взнос, без суммы и срока («дом — откладываю 5 000/мес»).
- **Закрытие долга** — тип цели; прогресс = уменьшение долга по счёту-долгу.
- **Приоритет целей** задаётся перетаскиванием; используется в сортировке и в тексте предупреждений.

### 6.8. Моделирование сценариев

- **Быстрый «что если»:** временно добавить или изменить событие → календарь и графики сразу показывают последствия → «применить» (становится реальным) или «отбросить».
- **Сохранённые именованные сценарии** — наборы изменений поверх базового плана.
- **Сравнение сценария с базовым:** таблица «цель → дата достижения: было / стало» + графики и диаграммы (линии остатка и т.п.).
- В сценарии можно менять разовые события, суммы регулярных, параметры целей.
- **Калькулятор накопления** (см. эталонный сценарий 4).

### 6.9. Категории

- **Многоуровневые** (дерево любой глубины). Событие может быть привязано к категории любого уровня или не привязано вовсе.
- **Стартового набора нет** — пользователь создаёт сам.
- Категория **необязательна**. Пустая = виртуальная «Без категории» во всех отчётах (не удаляется, не переименовывается, в событии не хранится).
- «Неучтённое» — отдельный тип события, а не категория; в диаграмме показывается отдельным сектором.

### 6.10. Интерфейс

- **Главный экран — три варианта, выбор в настройках:** календарь (**по умолчанию**), дашборд, таймлайн-лента.
  - Дашборд: «сходится ли план» (свободный остаток, ближайший разрыв, статус целей), график остатка, ближайшие события.
  - Таймлайн: вертикальная лента дней вперёд с событиями и остатком.
- **Масштабы календаря:** день, неделя, месяц, год.
- **Клетка дня:** сумма поступлений и сумма списаний; при наведении — детализация.
- **Подсветка дней:** красный — свободный остаток < 0; жёлтый — ниже настраиваемого порога; маркеры — обязательный платёж / зарплата / отчисление на цель.
- **Графики (все — в первой версии):** линия остатка во времени (с линиями сценариев), прогресс целей, доходы против расходов по месяцам, диаграмма по категориям (с секторами «Без категории» и «Неучтённое»).
- Вкладка «Счета» — счета с собственными графиками.
- **Первый запуск:** создание профиля → короткий мастер (основная карта и остаток → зарплата → обязательные платежи → цели), который можно пропустить; после мастера сразу виден прогноз.
- Переключение профилей (профили = разные люди).

### 6.11. Уведомления (системные уведомления macOS)

- За N дней до обязательного платежа.
- Напоминание сверить остаток (раз в N дней). Так как платформа только десктоп, эта функция критична: сверка должна занимать < 30 с.
- День отчисления на цель.

## 7. Эталонные сценарии (приёмочные вопросы к модели)

ТЗ должно гарантировать, что модель данных и движок прогноза способны ответить на эти вопросы:

1. «Если отложить машину на год (старт отчислений через 12 мес.), когда закроются кредитка и кредит на 100 000?»
2. «Отпуск за 6 месяцев: есть ли при этом плане месяц с кассовым разрывом? Если есть — на сколько надо сдвинуть отпуск?»
3. «Если закидывать на кредитку +5 000 сверху ежемесячно — на сколько раньше закрою?»
4. «Если откладывать на [любая цель / счёт] по [сумма] с периодичностью [день / неделя / месяц / квартал / год] — сколько будет через [период]? Какая будет общая финансовая ситуация с учётом всех уже имеющихся платежей и поступлений?»
5. (из требования индексации) «Как изменится прогноз, если повседневные траты на продукты будут плавно расти на 10% в год?»
6. (из исходного кейса) «Сейчас середина месяца, повседневка идёт выше плана — сколько не хватит к концу месяца и с какого дня свободный остаток уйдёт в минус?»

## 8. Объём первой версии и порядок сборки

**Решение заказчика:** все функции (26 пунктов + светлая/тёмная тема) входят в первую версию. Нарезка на MVP / v1.1 отклонена.

> **⚠ Риск (зафиксирован по требованию интервьюера):** объём первой версии большой — RRULE-движок, производственный календарь, сценарии со сравнением, 4 масштаба календаря, 3 главных экрана, 4 вида графиков, профили, Touch ID. Первое пригодное к ежедневному использованию состояние наступит поздно; до этого заказчик остаётся в Google-таблице. Митигация — этапность ниже.

**Порядок сборки (подтверждён заказчиком).** После каждого этапа приложение запускается и пригодно к использованию:

| Этап | Содержимое | Что получает пользователь |
|---|---|---|
| 1. Каркас | Счета, переводы, разовые и регулярные события (пресеты + список дат + окончание), календарь «месяц», светлая/тёмная тема, автобэкап | Календарь будущих платежей вместо таблицы |
| 2. Прогноз | Повседневка по шаблону, свободный остаток с резервами, красный/жёлтый, предупреждение о разрыве, график остатка, горизонт 20 лет | Ответ на «хватит ли до X» |
| 3. План/факт | Подтверждение событий, сверка остатка, «Неучтённое», фактический темп, уведомления | Честный прогноз изо дня в день |
| 4. Цели | Цели всех типов, приоритет, прогресс, график целей | «Когда накоплю / закрою» |
| 5. Сценарии | «Что если», калькулятор накопления, сохранённые сценарии, сравнение | Проигрывание решений |
| 6. Полнота | RRULE-конструктор, производственный календарь, индексация, перенос с выходных, 3 режима редактирования + история, категории и диаграмма по ним, день/неделя/год, дашборд и таймлайн, доходы против расходов | Всё остальное |

Профили, Touch ID и мастер первого запуска в этапы явно не распределены — см. открытые вопросы.

**Главная функция по мнению заказчика:** регулярные события (пресеты + произвольный список дат + окончание).
**По мнению интервьюера** ценность продукта для исходного кейса — свободный остаток + предупреждение о разрыве (этап 2). Противоречия нет: этап 1 — фундамент, этап 2 — ценность.

## 11. Риски, озвученные интервьюером и принятые заказчиком

1. **Только десктоп** → сверка остатка реже → отклонения ловятся позже. Принято осознанно.
2. **Только локальные данные** → при отказе диска/системы данные теряются (бэкап на том же компьютере). Принято.
3. **Отказ от MVP** → поздний выход на ежедневное использование. Митигация — этапность.
4. **Профили = разные люди, но Touch ID один на всё приложение** → профили не изолированы друг от друга по доступу: любой, кто прошёл Touch ID учётной записи macOS, видит все профили. Заказчик явно подтвердил: «1 приложение — несколько людей, Touch ID сразу на всё приложение». Изоляция профилей — только логическая (данные не смешиваются), не защитная.
5. **Удаление без корзины** → одна ошибка может стереть регулярное событие на 20 лет. Митигация — обязательный диалог подтверждения с масштабом удаления.
6. **Категории необязательны и без стартового набора** → диаграмма по категориям может состоять в основном из «Без категории». Принято; «Без категории» и «Неучтённое» показываются честно.
7. **Цели заказчика суммарно, вероятно, превышают его возможности** (см. §4). Это не риск продукта, а аргумент за функцию «сходится ли план».

## 12. Профили — уточнение

- Профиль = отдельный человек; у каждого свои счета, события, цели, категории, сценарии, настройки уведомлений.
- Создание профиля — первый шаг первого запуска, перед мастером.
- Защиты отдельного профиля (PIN и т.п.) нет — по решению заказчика.

## 13. Глоссарий

- **Карта-хаб** — основной счёт, куда приходит доход и откуда расходятся все платежи.
- **Счёт-долг** — счёт с отрицательным балансом-долгом, обновляемым вручную; основа цели «закрыть долг».
- **Резерв** — сумма на карте, зарезервированная под ещё не списанный обязательный платёж.
- **Свободный остаток** — остаток карты минус резервы; по нему работают сигналы.
- **Сверка** — ввод фактического остатка счёта на дату; задаёт опорную точку и порождает «Неучтённое».
- **Неучтённое** — системный тип корректирующего события, разница между расчётным и фактическим остатком.
- **Повседневка по шаблону** — плановые ежедневные траты, заданные правилами по дням недели.
- **Копилка** — цель без суммы и срока, только с взносом.
- **Сценарий** — именованный набор изменений поверх базового плана.

## 14. Открытые вопросы для агента ТЗ (не обсуждались — нужна рекомендация и подтверждение заказчика)

2. **Какие события «обязательные»** (порождают резерв) — флаг у события или по типу/категории?

4. **Профили, Touch ID и мастер первого запуска** — в какой этап сборки? (Рекомендация: создание профиля и Touch ID — этап 1; мастер — этап 2, когда появится прогноз.)

## 16. Приложение Б. Решения по открытым вопросам ТЗ (второй раунд интервью, 16.11.2026)

Закрывают раздел 13 ТЗ (В1–В27) и §14 брифа. Все решения подтверждены заказчиком.

**Приняты по рекомендации агента ТЗ без изменений:** В3 (значения по умолчанию), В4 (этапы), В5 (бэкап), В6 (подушка и дом — копилки), В7 (сценарии), В8 (индексация после «это и все следующие»), В13 (сверка — конец дня), В18 (индексация шаблона повседневки), В19 (macOS 13+, эталон M1 8 ГБ, неподписанный .dmg), В20 (восстановление через README + «Показать бэкапы в Finder», без функции восстановления в UI), В21 (фоллбэк на пароль macOS), В22 (уведомления при закрытом приложении, по всем профилям), В23 (клетка дня включает переводы; аналитика — нет), В24 (удаление категории — поддерево, события → «Без категории»; удаление профиля в первой версии не реализуется), В25 (граничные правила повторений), В27 (знак «Неучтённого»). В26 закрыт Приложением А.

**В1 + уточнение. Горизонт резерва.** Резервируются обязательные платежи с завтрашнего дня до дня, предшествующего следующему поступлению с признаком **«основной доход»**; платежи в день такого поступления не резервируются. Зарплате признак «основной доход» ставится автоматически (мастер, шаблон). Если основного дохода нет — окно 30 дней. *Причина уточнения:* без признака любой мелкий регулярный доход (кэшбэк) сжимал бы горизонт резерва.

**В2. Обязательные платежи.** Флаг «обязательный» у события, с умными умолчаниями (рассрочки/кредиты, переводы на счета-долги, платежи из мастера — включено). Флаг отвечает **только за резерв** и не влияет на аналитику.

**В9. Счета в прогнозе.** Сигналы, разрывы и свободный остаток — только по карте-хабу. «Всего доступно» (хаб + счета, помеченные доступными) — информационный показатель на вкладке «Счета» и дашборде.

**В10. Отдельные повседневные траты.** У траты признак «повседневная / внеплановая», по умолчанию «повседневная». Повседневные засчитываются в шаблон дня: списание дня = max(шаблон, Σ повседневных). Внеплановые — сверх шаблона.

**В11. Фактический темп.** Темп = (шаблон за период + отрицательное «Неучтённое» между сверками) / число дней между сверками. Основной прогноз — по шаблону; дополнительно линия «при текущем темпе». Сигналы — по основной линии; «дата ухода в минус при текущем темпе» — отдельный показатель (дашборд, календарь).

**В12. Первая сверка и ввод задним числом.** Первая сверка счёта задаёт стартовый остаток без «Неучтённого»; «Неучтённое» — со второй сверки. Событие, внесённое задним числом между сверками, пересчитывает «Неучтённое» последующей сверки (факт сверки не меняется) с уведомлением пользователю. Период до первой сверки показывается серым «до начала учёта», без красных/жёлтых сигналов.

**В14. Платежи по долгам.**
- Платёж по счёту-долгу (обязательный и «сверху») — всегда **перевод** с хаба на счёт-долг; обязательный — с флагом «обязательный». После погашения долга переводы на этот счёт в прогнозе прекращаются.
- В аналитике платежи по долгам — **не расход**, а отдельная линия «Платежи по долгам».
- Рассрочки без цели досрочного закрытия — регулярные списания с обязательной датой окончания, без счёта-долга.
- У регулярного списания есть признак **«рассрочка/кредит»** (ставится шаблоном создания кредита/мастером; делает дату окончания обязательной). В линию «Платежи по долгам» идут: переводы на счета-долги + списания с признаком «рассрочка/кредит». Аренда (обязательная, но не долг) — расход.

**В15. Отчисления на цели.**
- Отчисление — **реальный перевод** с хаба на счёт цели; участвует в прогнозе, резервах, разрывах, подтверждении.
- При переводе со счёта целей обратно на хаб приложение **предлагает распределение** (сначала нераспределённый остаток, затем цели с низшим приоритетом), пользователь подтверждает или меняет; последствие показывается сразу («Отпуск сдвинется на 2 мес»).
- Нераспределённый остаток (проценты, взносы без цели) виден на счёте и вручную распределяется по целям.

**В16. Эталон 1.** Высвобожденные деньги не перераспределяются автоматически; пользователь сам добавляет изменения в сценарий, приложение показывает «было / стало».

**В17. Эталон 2.** В «что если» поддерживаются оба действия: перенос начала отчислений и растягивание срока. Минимальный безопасный сдвиг автоматически не подбирается.

**Бэклог «после первой версии»:** автопредложение «Освободилось N ₽/мес — направить на цель с высшим приоритетом?»; кнопка «Найти минимальный сдвиг без разрыва».

**Трактовки на стыке решений (подтверждены заказчиком 16.11.2026):** (1) признак «повседневная/внеплановая» — только для разовых необязательных списаний; регулярные, кредитные и обязательные — всегда сверх шаблона; (2) отчисление на цель резервируется только при флаге «обязательный» (по умолчанию — у переводов на счета-долги); (3) флаг «обязательный» управляет резервом, маркером в календаре и уведомлением о платеже, не аналитикой; (4) без единой сверки статус «до начала учёта» не применяется; (5) платежи по долгам не входят в диаграмму по категориям; (6) регулярное снятие со счёта целей распределяется один раз на серию; (7) шаблоны кредита и зарплаты — пресеты создания события; (8) обязательный платёж по долгу — перевод (§6.1 исправлен).
